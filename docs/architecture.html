Summary

00The six calls

If you read nothing else, these are the decisions that shape everything downstream. Four of them push back on the plan as you described it.

  1. Split code from data. The folder you copy holds only Sheets, Docs and PDFs. The code is a standalone Apps Script project provisioned per school and pushed with clasp. "Copy the folder" stays true for the data — the code ships as a deployment, not as a file inside the folder.
  2. Each school owns its own Google account. Apps Script quotas are charged to the account that executes the script. If you own 500 schools' scripts, all 500 share your daily budget and you fall over somewhere around school #15. Their account, their quota, their storage, their liability — you sit on it as an editor.
  3. Build your own login. Parents in this market do not have Gmail accounts, and Google's identity API returns an empty string for anonymous web-app visitors anyway. Phone number + PIN, sessions in CacheService, every call re-checked on the server.
  4. Never give a teacher or parent Drive access. They get one URL and nothing else. All data isolation lives in your code, not in Drive sharing. The moment a class teacher is an editor on the fees spreadsheet, the product is over.
  5. Fees is the wedge, not report cards. Attendance and mark sheets win the demo. Fee collection, defaulter lists and printed challans win the cheque. Build the money module to production quality first.
  6. Append, cache, resume. Every write appends to a ledger where it can, every hot read comes from cache, every batch job checkpoints and resumes. That is the whole survival kit for a 6-minute execution limit.
Product framing

01What you're actually selling

Not software. You are selling a school's office running without a filing cabinet — and the thing that makes it sellable at this price point is that Google hosts it for free and you never run a server.

Be honest about the size envelope, because it determines who you say no to:

School sizeFitWhy
Under 100Works, hard to monetiseThey will keep using a register. Sell only if they ask.
100–1,200Sweet spotData volumes trivial, concurrency manageable, budget exists.
1,200–2,500StrainsResult-day concurrency and batch print windows start hurting. Needs Workspace.
2,500+Decline or re-platformYou are fighting the platform. Different product.

The strategic advantage of the Sheets backend is not cost — it is the escape hatch. When your software does not handle some edge case (a student admitted mid-term at a negotiated fee, a mark corrected after printing), the office clerk opens the sheet and fixes the row. No support ticket. No release. That single property is why this beats a "real" web app in a market where you cannot afford a support desk.

It is also the biggest liability, and §13 tells you how to defend against it.

Decision · tenancy

03Tenancy and deployment

This is where your "copy the folder and hooray" model needs one correction — after which it works better than you described it.

Decision 01

Does the deployable unit include the code?

  • noBound script inside a copied Sheet. Copy behaviour across the Drive API is inconsistent, the copy carries no deployment, and every school ends up with a silently forked codebase you cannot patch.
  • noApps Script library shared to all schools. Central updates, but Google's own docs warn that library calls slow execution measurably — and you would be paying that tax on every parent page load.
  • yesStandalone script per school, code pushed by clasp from one repo. Data folder is copied; code is deployed.

Why: it keeps runtime fast (no library indirection), gives every school an isolated data store and its own quota pool, and leaves you one git history as the source of truth. Updating 300 schools becomes a loop over 300 script IDs, not 300 manual copies.

Provisioning a new school

Target: under 15 minutes, mostly unattended. A script running in your account does steps 1–6.

  1. Recursively copy the template Drive folder into the school's Drive (folders, template Sheets, Docs templates, empty PDF archive tree).
  2. Create a standalone Apps Script project in the school's Drive via the Apps Script API.
  3. clasp push the current release tag into it.
  4. Write the school's Config sheet — name, logo file ID, academic year, grade scheme, fee heads, board, licence key, spreadsheet IDs.
  5. Create the web app deployment; record the URL.
  6. Register the school in your fleet registry: schoolId, scriptId, deploymentId, rootFolderId, version, licenceExpiry, studentCount.
  7. Hand over: principal signs into Google once to authorise the script, you seed staff accounts, bulk-import students from their existing Excel file.

Step 7 is the only genuinely manual part, and the student import is where every deployment actually burns its time. Build the importer — a column-mapping wizard that eats whatever malformed spreadsheet the school hands you — as a first-class module, not a script you run by hand. It is the difference between 15 minutes and two days per school.

The authorisation screen

The first time the principal authorises the script, Google shows an "unverified app" warning that looks alarming to a non-technical person. Script them through it with a one-page illustrated guide, or do it screen-shared during handover. Several deployments will stall here if you leave them alone with it.

Shipping updates to 300 schools

Rings, not a big bang:

  • Ring 0 — your own demo school, on every commit.
  • Ring 1 — three friendly schools, for a week.
  • Ring 2 — 20%, for a week.
  • Ring 3 — everyone.

A rollout is a loop over the registry: clasp push then create a new deployment version against each script ID. Every school's Config records the version it is on, and a daily trigger heartbeats back to you with version, student count and error count. That heartbeat is also your support dashboard — you find out a school's nightly job has been failing for a week before they call you.

Schema changes are the dangerous part. Keep an ordered, idempotent migrations[] array in the code, run it on first execution after an update, and follow one rule absolutely: add columns, never rename or reorder them. A clerk who has inserted a column by hand must not be able to break the release.

Decision 02

Who owns the Google account the system runs in?

  • noYou own everything, share it to the school. Total control and a clean kill-switch — but every school's execution burns your quota, and your Drive holds every school's student records. This collapses commercially and legally.
  • yesThe school owns its account and data; you hold editor rights on the script for updates.

Why: quota isolation is decisive, and "your data never leaves your own Google account" is a genuine sales line to a principal who is nervous about handing over student records. Push them onto Google Workspace for Education Fundamentals, which is free for accredited schools — it lifts every quota, gives staff real @school accounts, and makes identity trivial. Support consumer Gmail as the fallback tier, with a feature flag in Config.

Licensing, honestly

If the school owns the script, a technical person can open the editor and delete your licence check. Accept that. Practical posture:

  • Daily heartbeat validates the licence; on expiry, degrade rather than kill — watermark report cards, block the year rollover, disable bulk print. Never lock a school out of its own attendance data mid-term; that earns you a reputation you cannot recover from in a city where principals talk to each other.
  • Keep the renewal about things they cannot copy: board-format updates, new report card templates, WhatsApp delivery running through your API account, and support in Urdu on WhatsApp.
  • Do not over-invest in DRM. Your defence against piracy is that copying the code does not copy the service, and low-tier school owners are not going to maintain forked Apps Script.
Decision · security

04Identity, roles and scoping

You asked how modules get scoped by identity. The answer has one uncomfortable precondition: in this architecture, the server has full authority over everything, always. Access control is not a feature you add — it is the only thing standing between a parent and the whole school's records.

Decision 03

How do people log in?

  • noGoogle Sign-In. Parents in this market do not have Google accounts, and with a web app set to "anyone, even anonymous", Session.getActiveUser() returns an empty string — so it does not even work for the ones who do.
  • yesYour own identity table: phone number + PIN for parents, username + password for staff, signed session tokens. Google Sign-In becomes an optional upgrade for Workspace schools only.

Why: the phone number is the one identifier every parent in Karachi reliably has and remembers. It is also already in the school's admission register, so onboarding a parent requires no new data collection.

The three dimensions of access

Role alone is not enough — two class teachers have identical roles and must see different children. Model access as role × scope × field.

RoleDefault scopeSeesNever sees
PrincipalWhole schoolEverything, plus approvals and analytics—
Office adminWhole schoolAdmissions, records, documents, noticesSalary, staff appraisal
AccountantWhole schoolFees, receipts, concessions, defaultersMarks, discipline detail
CoordinatorOne wing (e.g. Primary)All classes in the wing, timetable, cover dutyOther wings, fee ledgers
Class teacherOne sectionOwn section's full profile, attendance, conductFee amounts, guardian CNIC
Subject teacher(class, subject) pairsMarks entry for own subjects onlyOther subjects' marks, all fees
ParentOwn childrenTheir child's results, attendance, fees, noticesAny other child, class rankings by name
StudentSelfTimetable, homework, own resultsFees, discipline reasons, staff notes

Session object

{
  userId:   "USR-0042",
  personId: "STF-0011",        // staff or guardian record
  role:     "subject_teacher",
  scope: {
    type: "subject_pairs",     // school | wing | section | subject_pairs | children | self
    ids:  ["9-A:MATH", "9-B:MATH", "10-A:MATH"]
  },
  year: "2026-27",
  exp:  1788000000
}

Scope IDs are resolved at login from the assignment tables and baked into a signed token, so the hot path costs no extra sheet reads. Bump a version counter in PropertiesService whenever assignments change; tokens issued before the bump are re-resolved on next use.

The guard contract

One function, called first in every single endpoint, no exceptions:

guard(token, "marks.enter", { classId: "9-A", subjectId: "MATH" })
  → returns session, or throws

// It checks three things, in order:
//   1. token valid and unexpired
//   2. role holds the permission "marks.enter"   (matrix in Config)
//   3. the target falls inside session.scope.ids  (the part everyone forgets)

Step 3 is where real systems leak. A teacher who can enter marks for 9-A can trivially edit the request to say 10-C; only an explicit scope check stops them. Make it impossible to skip by having the repository layer require a session argument — a function that reads marks without one should not exist.

The permission matrix itself lives in a Config sheet (rows = roles, columns = permission keys), so a school that wants its class teachers to see fee status can be accommodated without a code change. Field-level filtering is a per-role allowlist applied on the way out: project(studentRow, session) strips guardian CNIC and fee balance before a teacher's payload ever leaves the server.

Threat model, plainly

Anonymous web app + owner authority means your login endpoint is internet-facing and protects real children's records. Minimums: PIN lockout after 5 failures, per-phone rate limiting in CacheService, tokens that expire in hours not weeks, no PII in URLs (it lands in browser history on shared family phones), and salted iterated hashing for PINs — never plaintext, never a bare single-pass hash.

A 4-digit PIN is weak by any standard. It is also the only thing this market will actually use. Compensate with lockout and rate limiting rather than pretending a stronger policy will survive contact with parents.

Decision 04

One spreadsheet or many?

  • noOne workbook with 40 tabs. Simple to reason about; every write locks the whole file, opening it in a browser takes 20 seconds by March, and one bad edit corrupts everything.
  • yesSplit by domain, and by academic year for transactional data.

Why: lock contention is per-spreadsheet. The accountant recording a payment should never block a teacher saving attendance. Year-splitting also means archiving a finished year is one file move, and last year's 200,000 attendance cells never slow down today's lookup.

Identifier strategy

Never use row numbers as identity — a clerk sorting a sheet would silently reassign every child's record. Use human-readable, immutable string keys:

  • STU-2026-0417 — internal student key, never reused, never changes even if the child leaves and returns
  • GR No. — the school's own General Register number, kept as a separate field because schools reuse and reformat it and you cannot control that
  • STF-0032, GRD-0891, INV-2026-08-0417, RCPT-2026-004512

  enrollment_id · student_id · year · class_id · section · roll_no
  result(promoted|detained|left) · final_percentage
Why Enrollment is separate from Students

A student's class changes every year. If you store class on the student row you destroy history the moment you promote them, and last year's report card becomes unreproducible. Students holds identity; Enrollment holds "who was in which section in which year". Every year-scoped query joins through it.

Ledgers, not mutable balances

Fees and discipline are both append-only ledgers. You never update a balance field — you append a row and reduce over it. Two payments landing in the same second cannot corrupt each other, corrections are recorded rather than hidden, and the audit trail is free:

FeePayments   append only, never edited
  payment_id · student_id · invoice_id · date · amount · mode(cash|bank|jazzcash|easypaisa)
  reference_no · received_by · receipt_no · reversal_of(payment_id or blank) · note

// balance = Σ invoices − Σ payments (excluding reversed pairs)
// a mistaken entry is corrected by appending a reversal, never by deleting
Rule: no formulas in data sheets

Zero =SUM(), zero VLOOKUP, zero conditional formatting that carries meaning. All computation happens in code. Formulas break the instant a clerk inserts a row, they make batch writes 10× slower, and they produce numbers your code disagrees with. Data sheets hold raw values only. Build a validateSchema() that runs on load and screams if a header moved.

Deep dive

07Exams, mark sheets and report cards

The highest-stakes module in the product. A wrong mark on a printed report card is the one bug a principal will not forgive, so the workflow matters more than the code.

The entry-to-print pipeline

  1. Exam definition — term, applicable classes, subject list with max marks and weightage, entry deadline.
  2. Marks entry — subject teacher, own (class, subject) pairs only, one grid per section. Validation on every cell: numeric, within 0–max, or flagged absent. Autosave per row.
  3. Class teacher verification — sees the full section across all subjects, spots the blanks and the impossible totals, flags back to subject teachers.
  4. Exam controller locks — the (exam, class, subject) tuple is frozen. After this point an edit requires principal override and writes an audit row naming who changed what from what to what. This single feature prevents the classic disaster: marks quietly changed after report cards were printed.
  5. Compilation — totals, percentage, grade from the school's scheme, position in section and class with explicit tie handling, pass/fail against per-subject minimums, promoted/detained.
  6. Print — batch, by section.
  7. Publish — a separate flag. Report cards are visible to parents only when the principal publishes, never when they are generated.

Ship the standard Pakistani board grading as the default and make it fully editable per school, since private schools invent their own bands constantly:

GradeA1ABCDEF
Percentage80+70–7960–6950–5940–4933–39<33

Generating 600 PDFs without dying

Two paths, and choosing the right one per situation is the whole trick:

Batch print — one PDF per section
Build a single document containing all 40 students in the section, separated by page breaks, then export it once as PDF. One file to open, one to send to the printer, roughly 40× fewer Drive operations than generating individual files. This is what the office actually wants: they print class by class.
Parent portal — one PDF per child
Generated lazily on first request and cached in Drive, or pre-generated overnight for the whole school after publish. Never generated synchronously while a parent waits.

For the rendering itself, HTML gives you far more layout control than Docs placeholder replacement — and Apps Script can convert an HTML blob straight to PDF, which handles the table-heavy, tightly-boxed layout a report card needs (and gets you page-break-after for the batch case). Keep the Docs template path as the authoring-friendly fallback for schools that want to fiddle with their own wording.

Set the Urdu fields in Noto Nastaliq Urdu and test the render early — bilingual name rendering is the detail that makes a report card look legitimate to a Karachi parent, and it is much easier to get right at the start than to retrofit.

08Fees — the module that sells

A principal will tolerate clunky attendance. They will not tolerate not knowing who owes what. Build this one properly and the rest of the product rides along.

Structure

  • Fee heads — tuition, admission, annual charges, exam, transport, lab, late fine. Each with a frequency (monthly, annual, one-time) and whether it is concession-eligible.
  • Structure per class, overridable per student — because negotiated fees are universal in this market and pretending otherwise makes the software useless on day one.
  • Concessions — sibling discount, staff child, scholarship, hardship. Each with a principal approval record and an expiry.

Cycle

  1. Monthly invoice generation (batch job, resumable) on a fixed day.
  2. Challan PDF with three tear-off copies — bank, school, parent — carrying the school's bank details, the due date and the late-fine rule. Batch print by section, and a per-student copy in the parent portal.
  3. Payment recording: cash at the office window, bank deposit slip, JazzCash/Easypaisa reference. Every payment gets a sequential receipt number that cannot skip.
  4. Late fine applied automatically after the due date, with a per-school toggle and a waiver action that requires a reason.
  5. Defaulter list — by class, by amount, by months overdue. The single most-used screen in the product.
  6. Daily collection reconciliation for the accountant: opening, receipts by mode, closing, signed off. Month close locks the period.
Messaging reality

You cannot email 600 parents from a Gmail account (100/day), and SMS gateways cost money per message. For phase 1, generate WhatsApp click-to-send links (wa.me with a pre-filled message) as a batch the office clerk works through — free, and it fits how these schools already communicate. Automated sending needs the WhatsApp Business Cloud API with per-conversation pricing; make that a paid add-on you run through your own account, which conveniently is also a renewal lever.

09Discipline points

You described this as every teacher being able to give plus and minus points. That works — but unbounded, it becomes a weapon within a month and parents start arriving at the office. The design is mostly guardrails.

The ledger

DisciplineLedger   append only
  entry_id · timestamp · student_id · awarded_by(staff_id) · category
  points(+/−) · reason_text · evidence_file_id · reversal_of · reviewed_by

Guardrails that make it survivable

  • Point authority by role. Subject teacher ±5 per entry, class teacher ±10, coordinator ±20, principal unlimited. A teacher cannot end a child's term in one tap.
  • Daily cap per teacher. No more than, say, 15 negative points issued per teacher per day across all students — a teacher having a bad day cannot carpet-bomb a class.
  • Mandatory reason above a threshold. Anything beyond −3 requires typed text, not just a category chip.
  • Automatic parent notification on any negative entry past a configured threshold, so nothing accumulates invisibly and lands as a shock on the report card.
  • Reversal, never deletion. A wrong entry is corrected by appending a reversal that names the reviewer. The original stays visible to admin.
  • Appeal flow. Parent taps "request review" → coordinator sees a queue → resolves with a note. This one feature converts the module from a conflict generator into a trust generator.

Making it two taps on a phone

Teachers will not use this if it takes thirty seconds. The teacher app flow: pick section → tap student photo → tap a preset chip (Homework not done −2, Helped a classmate +3, Late −1, Excellent participation +5). Presets and their values are configured per school. Free-text is the exception path, not the default.

What the points feed

  • A conduct grade on the report card, derived from net points over the term against configurable bands — this is what makes teachers bother to enter data, because it visibly matters.
  • House points totals, which schools love for assembly announcements.
  • A coordinator dashboard of students trending sharply negative — the actual pastoral-care value, and worth surfacing prominently.

10Attendance and timetable

Attendance

Store it wide: one row per student per month, 31 day-columns holding single-character codes (P A L E H — present, absent, leave, excused, holiday). That is 600 rows per month instead of 13,000, roughly 30× cheaper to read and write, and it prints as a monthly register that looks exactly like the paper one the school already uses.

The teacher screen must mark a full section in under 30 seconds: default everyone present, tap only the absentees, submit. One write. Period-wise attendance for secondary classes is a phase-3 option — most schools at this tier will not sustain it.

Derived automatically: monthly percentage per student, consecutive-absence alerts to the parent, the monthly register PDF, and the attendance figure that appears on the report card.

Timetable

Decision 05

Automatic timetable generation, or assisted manual?

  • noAuto-generate from constraints. It is a genuinely hard scheduling problem, it will not finish inside 6 minutes for a 25-section school, and the output always violates some unstated rule the coordinator holds in their head.
  • yesA grid editor with live clash detection. The coordinator drags periods; the system refuses double-booked teachers and rooms, tracks per-teacher load against their maximum, and flags subjects short of their weekly quota.

Why: the coordinator already knows the timetable they want — they just cannot spot conflicts across 25 sections on paper. Validation delivers 90% of the value for 10% of the work, and it ships this quarter rather than next year.

The feature that actually wins coordinators over is substitution management: a teacher is absent, the system lists free teachers for each of that teacher's periods, the coordinator assigns cover in a minute, and a daily cover list prints for the staff room. This is a daily pain and nobody at this tier has it solved.

Deep dive

11Year rollover

The module everybody forgets and everybody needs once a year. Done wrong, it destroys the school's history — which is the one unrecoverable failure in this product.

What it has to do, as an atomic, reviewable, resumable operation:

  1. Close the outgoing year: lock exams, finalise results, mark promoted / detained / left per student.
  2. Create the new year's spreadsheets from templates and register their IDs in Config.
  3. Create new Enrollment rows: promoted students into the next class, detained students repeating, leavers excluded.
  4. Re-section and re-assign roll numbers — with a manual review screen, because principals always want to rebalance sections by hand.
  5. Carry forward outstanding fee balances as opening dues, with a report of who and how much.
  6. Roll over staff assignments and the timetable as a starting draft.
  7. Archive the previous year's folder as read-only and leave it fully browsable.

Design rules: preview before commit (show exactly what will happen to how many students, and let it be cancelled), full snapshot backup immediately before, and idempotency so a half-finished rollover can be safely re-run. Then walk the first ten schools through it personally — it is the highest-risk operation in the calendar and the fastest way to lose a customer.

Patterns

13Survival patterns

Seven techniques that Apps Script projects either adopt or die of. Build each once, centrally, before the modules.

Batch every sheet operation
One getValues() for the range, work in memory, one setValues() back. A loop of per-cell reads is 100× slower and is the single most common reason an Apps Script app feels broken.
Lock every write
LockService.getScriptLock() around the read-modify-write, held for as short a window as possible, with a bounded wait and a clear error if it times out. Sheets has no transactions; this is all you get. Append-only ledgers sidestep most of the need.
Cache hot reads
Student index, timetable, permission matrix, fee structure — all read constantly, changed rarely. Keep them in CacheService keyed with a version counter from PropertiesService; any write bumps the counter and every cache entry invalidates at once. Watch the per-key size cap and chunk anything large.
One generic job runner
A Jobs sheet holding job_id, type, params, cursor, total, status, started_by, plus the checkpoint-and-resume trigger loop from §7. Report cards, invoicing, rollover and bulk import all become job types rather than four separate hand-rolled batch systems.
Audit everything that mutates
Append-only: timestamp, user, role, action, entity, before, after. Non-negotiable for marks and money. The day a principal accuses a clerk of changing a fee record, this sheet is the entire value of your software.
Nightly backup
A trigger copies every data spreadsheet into _Backups/YYYY-MM-DD/ with 30-day rolling retention, plus a monthly CSV export. Drive's own version history is a second net. A school that loses a term of attendance will not renew, and will tell every other principal in the neighbourhood.
Keep an exit ramp
All SpreadsheetApp calls live in a repository layer (repo_students.gs, repo_fees.gs). Services never touch a spreadsheet directly. If you outgrow Sheets at school #400, you swap the repositories for a real database and the business logic survives. This costs almost nothing now and is the difference between a pivot and a rewrite.

Two Apps Script quirks worth designing around: all .gs files share one global scope with no module system, so wrap each unit in a namespace object (var Fees = (function(){ … })();) to avoid collisions; and file load order is alphabetical, which is why bootstrap carries a numeric prefix.

Working setup, which is what we have already stood up in this session: clasp is installed and authenticated against your account, so the loop is edit → clasp push → test in the dev school → tag → rollout.js ring1. Keep .clasprc.json out of git — it is a live credential.

Testing

Apps Script has no real test framework. Build a test.gs with plain assertion functions runnable from the editor against a disposable school, and a seedDemoSchool() that generates 600 fake students with Pakistani names, a full term of attendance and a term of marks. You will run that seeder hundreds of times, and it doubles as your sales demo.

The one that should worry you most is not technical. It is that a school pays, uses it for a term, and then the office quietly drifts back to the paper register because one workflow was slower than what they had. Instrument usage — the heartbeat should report attendance-marking rate and fee entries per week — and treat a school going quiet as a support emergency, not a happy customer.

Open

16Decisions I need from you

Everything above I could settle from the brief. These I cannot, and each one changes what gets built first.

  1. Consumer Gmail or Workspace for Education? If you can get schools onto free Education Fundamentals, quotas stop being an architectural constraint and identity gets much simpler. If not, every design above stays as written. This is the single highest-leverage question.
  2. Who owns the account — school or you? I have recommended the school. If you want a kill-switch badly enough to own it yourself, say so now, because it changes the entire quota and provisioning model.
  3. Urdu in the interface, or only on printed output? Bilingual UI roughly doubles the copywriting and testing surface. My default: English UI, bilingual documents.
  4. Which board and grading conventions do your first ten schools follow? BSEK, Aga Khan Board, or their own internal scheme? Report card format is the thing they will judge you on in the first meeting.
  5. What are they paying today, to a clerk or to existing software? That number sets the price and tells us whether fees or report cards is the sharper wedge.
  6. Do you have one friendly school to build against? Building this against a real school's actual data beats any amount of speculative design — and their existing Excel file will teach us more about the schema than another week of planning.

An eight-week MVP aimed at one real school: student records with the import wizard, fees end to end including printed challans, attendance, exams through to batch-printed report cards, and the parent portal. That is a complete, sellable product. Timetable, discipline and messaging come after the first school is live and paying, and they will be better modules for having watched a real office work.
